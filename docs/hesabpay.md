# پرداخت آنلاین با حساب‌پی (HesabPay) — وضعیت، چه ساخته شد، کارهای مانده

> به‌روز: ۳ قوس ۱۴۰۵ (۲۰۲۶-۱۱-۲۴).
> **خلاصه:** درگاه حساب‌پی **از روی مستندات رسمی ساخته شد** (چاپ صفحه‌های `docs.hesab.com` که صاحب پروژه در `resources/hesabpay/` گذاشت؛ این پوشه به GitHub نمی‌رود). تا وقتی **کلید API** در `.env` نیست، سایت آن را به مشتری نشان نمی‌دهد. **هنوز با حساب واقعی آزمایش نشده است**، پس «کار می‌کند» گفته نمی‌شود تا آزمایش sandbox و یک پرداخت کوچک واقعی انجام شود.

## ۱. آنچه از مستندات رسمی گرفته شد

| موضوع | از مستندات |
|---|---|
| آدرس API | sandbox: `https://api-sandbox.hesab.com`، production: `https://api.hesab.com` |
| کلید | هدر `Authorization: API-KEY <key>`؛ از «Developer ← API Key» پورتال؛ فقط سمت سرور |
| ساختن نشست | `POST /api/v1/payment/create-session`. فیلدها: `items[]` (۱ تا ۲۰ قلم؛ `id` ≤۵۰، `name` ≤۵۰۰، `price` با حداکثر ۲ رقم اعشار؛ **فیلد تعداد ندارد**؛ جمع ≤ ۹۹۹٬۹۹۹٫۹۹ افغانی)، `user_id` (مرجع ما، ≤۵۰)، `email` (اختیاری)، `redirect_success_url`، `redirect_failure_url`. جواب: `session_id`، `url`، `expires_at` |
| مدت نشست | **۱۵ دقیقه** از ساختن (نه از باز کردن) |
| روش‌ها | کیف‌پول حساب‌پی (کمترین ۱۰ افغانی)، کارت AfPay (برای مهمان حداکثر ۱۵٬۰۰۰ افغانی در هر پرداخت و ۱۰ خرید در ۷ روز)، کارت بین‌المللی (از حدود ۴۰ افغانی؛ اگر برای حساب ما روشن شود). همه به افغانی |
| برگشت مرورگر | موفق ← آدرس موفق؛ ناموفق/لغو/نامعلوم ← آدرس ناموفق با پارامتر `data` (JSON: `success:false`، `status`، `reason`، `message`، `session_id`، `transaction_id`، `user_id`). **شاهد پرداخت نیست**؛ مشتری می‌تواند عوضش کند |
| پیام سرور-به-سرور (webhook) | POST با JSON. **امضا و timestamp داخل خود JSON است** و فقط با `POST /api/v1/hesab/webhooks/verify-signature` نزد خود حساب‌پی بررسی می‌شود. رویدادها: `payment_success`، `payment_failure`. پورتال یک پیام آزمون `type: "webhook.validation"` هم می‌فرستد |
| تکرار پیام | اگر جواب ۲۰۰ نگیرد، تا ۵ بار دیگر (۱، ۲، ۵، ۱۰ و ۳۰ دقیقه بعد)، هر بار با امضای تازه. کلید بی‌تکراری = شماره‌ی تراکنش، نه امضا |
| بررسی تراکنش | `GET /api/v1/hesab/get/transaction-detail/{transaction_id}`. `success:true` یعنی «پیدا شد»، نه «پرداخت شد» |
| بازپرداخت | `POST /api/v1/hesab/refund/transaction`. **فقط کامل** (جزئی ندارد)، **رمز چهاررقمی کیف‌پول رمزشده** لازم است، کلید بی‌تکراری ندارد |
| تأیید دامنه | در production، از «تاریخ اجرای قانون دامنه» به بعد: دامنه‌ی سایت با رکورد DNS TXT تأیید شود، آدرس‌های برگشت و webhook با HTTPS روی همان دامنه باشند، و مشتری از صفحه‌ی همان دامنه به حساب‌پی برود (Referer). در sandbox هیچ‌کدام لازم نیست |
| چندفروشنده‌ای | `Multi-Vendor Transfer` بعد از تأیید پرداخت، پول را بین حساب‌پی فروشندگان تقسیم می‌کند (ساخته نشد؛ پایین را ببینید) |

## ۲. آنچه ساخته شد (۳ قوس ۱۴۰۵)

| چیز | کار |
|---|---|
| `App\Services\Payments\Gateways\HesabPayGateway` | ساختن نشست (یک قلم «سفارش … از بازارک» با **مبلغ نهایی سفارش**، تا جمع دقیقاً همان مبلغ باشد و تخفیف و کرایه هم داخلش)، بررسی امضای پیام نزد حساب‌پی، بررسی تراکنش برای مدیر. `isReady()` فقط با کلید |
| `App\Services\Payments\OnlinePaymentService` | `begin` (نشست تازه یا همان نشست هنوز معتبر)، `handle` (اعمال یک‌باره‌ی پیام)، `switchToCash`، `cancelStale` |
| `POST /webhooks/hesabpay` (`HesabPayWebhookController`) | بی CSRF. امضای نادرست ← ۴۰۱ و هیچ تغییری. آزمون پورتال ← `{"success": true}`. پیام پرداخت ← اعمال و ۲۰۰؛ تکراری ← ۲۰۰ بی اثر |
| جدول `payment_events` | هر پیام یک بار (`provider` + `event_id` یکتا)، با نتیجه و «نیاز به بررسی»؛ امضا ذخیره نمی‌شود |
| ستون‌های `payments.gateway_session_id` و `gateway_checkout_url` | نشست ۱۵ دقیقه‌ای؛ شماره‌ی تراکنش بعد از پرداخت در `provider_reference` |
| صفحه‌ی تسویه | اگر روش «حساب‌پی» روشن و کلید باشد، دیده می‌شود. بعد از «ثبت سفارش» مشتری مستقیم به صفحه‌ی حساب‌پی می‌رود |
| صفحه‌ی سفارش | «منتظر پرداخت آنلاین» با دو دکمه: **«پرداخت با حساب‌پی»** (دوباره) و **«نمی‌خواهم آنلاین بپردازم؛ نقد می‌دهم»** (درِ خانه ← پیک، حضوری ← نمایندگی) |
| برگشت از حساب‌پی | `/payment/hesabpay/{uuid}/return` و `/failed`: **فقط پیام**، هیچ وضعیتی عوض نمی‌شود. متن پیام حساب‌پی به‌شکل متن ساده نشان داده می‌شود |
| لغو خودکار | `payments:cancel-unpaid-online` هر ۱۰ دقیقه: سفارش آنلاینی که تا **۱۲۰ دقیقه** پرداخت نشد لغو می‌شود و موجودی و کد تخفیف آزاد می‌شود (`ONLINE_PAYMENT_CANCEL_MINUTES`) |
| پنل | «سفارش‌ها ← **پیام‌های حساب‌پی**» (فقط صاحب و مدیر)، با عدد سرخ برای «نیاز به بررسی» و دکمه‌ی «بررسی شد». در صفحه‌ی هر پرداخت: شماره‌ی تراکنش و دکمه‌ی **«بررسی با حساب‌پی»** (فقط نشان می‌دهد) |
| تست | `HesabPayTest` (۱۱ تست، همه با حساب‌پی ساختگی `Http::fake`؛ هیچ اتصال واقعی) |

**قاعده‌های پول (همه در کد و تست):**
- فقط پیام **امضاشده و تأییدشده نزد حساب‌پی** پرداخت را «پرداخت‌شده» می‌کند. برگشت مرورگر هرگز.
- مبلغ پیام باید **دقیقاً** مبلغ پرداخت باشد؛ وگرنه پرداخت‌شده نمی‌شود و «نیاز به بررسی» می‌خورد.
- پیام رد، پرداخت‌شده را هرگز پایین نمی‌آورد. بعد از رد، سفارش منتظر می‌ماند تا مشتری دوباره بپردازد.
- این حالت‌ها پرداخت‌شده نمی‌شوند و «نیاز به بررسی» می‌خورند؛ مدیر پول را از داشبورد حساب‌پی پس می‌دهد:
  - پول برای سفارش لغوشده یا سفارشی که به نقد عوض شده؛
  - پول دوم برای یک سفارش؛
  - پیامی که سفارشش پیدا نشد.
- طلب فروشنده از پرداخت آنلاین مثل پول نمایندگی است: بعد از «تحویل شد» + «روزهای انتظار پیش از تسویه».

## ۳. عمداً ساخته نشد

- **بازپرداخت از راه API:** رمز کیف‌پول را می‌خواهد و جزئی ندارد. فعلاً از داشبورد حساب‌پی پس داده می‌شود و در پنل «بررسی شد» زده می‌شود. اگر بعداً خواستید، رمز را مدیر هر بار وارد می‌کند و هیچ‌جا ذخیره نمی‌شود.
- **تقسیم خودکار پول بین فروشندگان (Multi-Vendor):** تسویه‌ی فروشنده‌ها فعلاً دستی و با دفتر خودمان است. ساختن آن به حساب‌پی هر فروشنده و تصمیم شما بسته است.
- **پرسش خودکار وضعیت از حساب‌پی:** معنای `data.status` در جواب «بررسی تراکنش» (مثلاً `1`) در مستندات فقط «نمونه» است. تا حساب‌پی معنایش را نگوید، از آن «پرداخت‌شده» ساخته نمی‌شود.

## ۴. کارهای صاحب پروژه

۱. **دسترسی به پورتال حساب‌پی** (حسابتان بلاک شده بود و ایمیل داده‌اید). بعد از باز شدن:
   - در **sandbox developer portal** وارد شوید ← Developer ← **API Key** ← کلید تازه بسازید.
   - کلید را **فقط به من بدهید که در `.env` بگذارم** (یا خودتان در `.env` بنویسید: `HESABPAY_ENV=sandbox` و `HESABPAY_API_KEY=…`). هیچ‌جای دیگر (واتساپ عمومی، GitHub، عکس) نگذارید.
۲. **آزمایش sandbox:** پیام webhook از انترنت به لپتاپ نمی‌رسد. پس آزمایش کامل بعد از گذاشتن سایت روی سرور (یا با یک تونل موقت مثل Cloudflare Tunnel) است. در پورتال ← Developer profile ← **Webhooks**: آدرس `https://<دامنه>/webhooks/hesabpay` را برای هر دو رویداد `payment_success` و `payment_failure` ثبت کنید.
۳. **حساب پذیرنده‌ی production:** شرایط و مدارک را از حساب‌پی بپرسید. از آن‌ها بپرسید:
   - کارمزد هر روش (کیف‌پول، AfPay، کارت بین‌المللی) چند است و از کدام طرف کم می‌شود؟
   - پول کِی به حساب ما می‌رسد؟
   - کارت بین‌المللی برای حساب ما روشن می‌شود؟
   - `DOMAIN_ENFORCEMENT_DATE` چه تاریخی است؟
   - در جواب «بررسی تراکنش»، `data.status` چه مقدارهایی دارد و کدام یعنی «موفق»؟
۴. **دامنه:** بعد از خرید دامنه، در پورتال production ← Registered domains ← دامنه را اضافه کنید ← رکورد **TXT** را در DNS بگذارید ← Verify. سایت باید **HTTPS** باشد.
۵. **روشن کردن:** بعد از آزمایش، در پنل «روش‌های پرداخت» روش «پرداخت آنلاین با حساب‌پی» را روشن کنید و یک **پرداخت کوچک واقعی** (مثلاً ۲۰ افغانی) بکنید و در «پیام‌های حساب‌پی» ببینید «پرداخت تأیید شد».

## ۵. روی سرور (یادآوری برای راه‌اندازی)

- `.env`: `HESABPAY_ENV=production`، `HESABPAY_API_KEY=…`، `APP_URL=https://…`.
- cron هر دقیقه: `php artisan schedule:run` (برای لغو خودکار سفارش‌های پرداخت‌نشده).
- `Referrer-Policy: strict-origin-when-cross-origin` (همین حالا هست) تا حساب‌پی دامنه‌ی ما را ببیند.
